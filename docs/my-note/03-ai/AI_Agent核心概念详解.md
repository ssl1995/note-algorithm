## 一、LLM 和 Agent 有什么区别？
### 什么是 LLM？
LLM（Large Language Model，大语言模型）是通过学习海量文本数据、掌握人类语言规律和知识的模型。ChatGPT、Claude、DeepSeek、文心一言等底层都是大语言模型。
LLM 的工作原理本质是「预测下一个字」：根据学到的语言规律逐字生成。因为训练数据量巨大，效果惊人，能写文章、写代码、做翻译、回答专业问题。
### LLM 的四大弊端
1. **只会「说」不会「做」**：能力被困在对话框里，无法与外部世界互动、操作任何系统。
2. **没有「记忆」**：记忆只限于当前对话的上下文窗口，对话结束一切归零。
3. **不会用「工具」**：不能上网搜索、查数据库、调 API，所有回答来自训练数据，存在知识截止日期和「幻觉」问题。
4. **不会「规划」**：是「被动响应型」，问一句答一句，无法自主拆解任务、制定计划、分步执行。
### 那 Agent 是什么？
**Agent（智能体）就是 LLM 在循环中自主使用工具的系统。**
三个关键词：
- **LLM**：Agent 的核心大脑还是大模型；
- **工具**：能调用外部能力；
- **循环**：不是一问一答就结束，而是不断思考、行动、观察结果、再思考，直到任务完成。
类比：LLM 是只给建议的顾问，Agent 是能动手干活的项目经理。
### Agent 怎么解决 LLM 的弊端？
- 针对「只会说不会做」：引入**工具调用**能力，可调用搜索引擎、数据库、API、代码执行器等。
- 针对「没有记忆」：配备**记忆系统**，包括短期记忆（当前任务上下文）和长期记忆（外部数据库，跨对话保留）。
- 针对「不会用工具」：业界推出 MCP 等**标准化协议**统一工具接入方式。
- 针对「不会规划」：具备**任务拆解和规划**能力，把大目标分解为小步骤逐步执行。
### Agent 的核心组成（四大模块）
1. **大脑**（LLM）：理解意图、推理判断、决定下一步行动；
2. **规划模块**：把复杂任务拆解成可执行步骤；
3. **记忆模块**：存储和检索信息，保持长任务中的连贯性；
4. **工具模块**：Agent 的「手和脚」，与外部世界互动。
本质区别总结：**LLM 告诉你「怎么做」，Agent 直接帮你「做完了」**。
## 二、Agent 和 Workflow 有什么区别？
### 两者的定义
- **Workflow（工作流）**：LLM 和工具通过预定义的代码路径进行编排的系统。
- **Agent**：LLM 动态主导自身流程与工具调用的系统，由 LLM 自主决定如何完成任务。
大白话：Workflow 是「开发者告诉你每一步该做什么」，Agent 是「我告诉你目标，你自己决定怎么做」。
类比：Workflow 像工厂流水线（每个工位提前设计好），Agent 像自主工作的项目经理（自己调研、定计划、协调资源、推进执行）。
### 核心区别：谁在控制流程
| 维度 | Workflow | Agent |
|:---|:---|:---|
| 控制权 | 在代码手里 | 在 LLM 手里 |
| 行为特征 | 确定、可预测、可复现 | 动态、灵活、能适应变化 |
| 成本 | token 消耗省（约为 Agent 的 1/4） | 反复推理决策，token 消耗高 |
| 可靠性 | 出问题容易定位 | 决策路径不确定，调试困难 |
### 什么时候用 Workflow，什么时候用 Agent？
Anthropic 的建议：**从最简单的方案开始，只在明确需要时才增加复杂度。**
- 任务步骤固定、可提前规划，或对可靠性要求高（金融交易、医疗系统）→ 用 Workflow；
- 任务开放式、无法预知所有步骤、需灵活应对意外 → 用 Agent。
实际生产中最常见的是**混合架构**。正如 LangChain 所说："大多数生产中的 Agent 系统其实是 Workflow 和 Agent 的组合。"例如智能客服：整体流程用 Workflow 控制（接收工单→分类→处理→回复），复杂问题的「处理」环节启动 Agent 自主分析解决。
## 三、Agent 有什么工作模式？
### 模式一：ReAct（边想边做）
ReAct = Reasoning + Acting（推理 + 行动），最经典、最基础的 Agent 工作模式，几乎所有主流 Agent 框架底层都在用。
核心是一个三步循环：
1. **思考（Thought）**：分析当前情况，决定下一步做什么；
2. **行动（Action）**：调用一个工具执行；
3. **观察（Observation）**：查看工具返回的结果，再回到思考，循环直到任务完成。
优点：透明可审计、灵活适应、通用性强。
缺点：token 消耗大（每步都要完整推理）；有时会陷入循环走不出来。
### 模式二：Plan-and-Execute（先想好再做）
分两阶段：先一次性规划出完整执行计划，再按计划逐步执行，不用每步重新思考全局。
优点：**省钱**，token 消耗约为 ReAct 的 1/5。
缺点：不够灵活，执行中情况变化时原计划可能失效。改进做法：加入「重新规划检查点」，每隔几步检查计划是否还靠谱。
### 模式三：Reflection（做完再检查）
完成任务后不急着交付，先自我检查。两种实现方式：
1. **自我反思**：同一 Agent 切换到「审查者」角色审视自己的输出，发现问题就修改，直到满意；
2. **双 Agent 对话**：一个负责生成，一个负责评审，来回迭代（类似 Code Review）。
适合对质量要求高的场景：代码生成、法律文书、学术论文等。
### 模式四：Multi-Agent（团队协作）
多个专业化 Agent 各司其职、协作完成复杂任务（规划、搜集信息、写代码、测试等）。
主流多 Agent 框架：LangGraph、CrewAI、OpenAI Agents SDK、微软 AutoGen 等。
Anthropic 提醒：**不要过早引入多 Agent 架构**，一个强大的单 Agent 往往够用，只有任务确实需要拆成多个并行子任务时才值得引入。
总结：几种模式不互斥，实际中常组合使用（多 Agent 系统中每个 Agent 内部用 ReAct，整体协作是 Multi-Agent，最后加 Reflection 检查质量）。
## 四、Function Call 是什么？
**Function Call（函数调用）**是 OpenAI 在 2023 年 6 月率先推出的能力：让 LLM 不仅能生成文字，还能告诉外部程序「我想调用某个函数，参数是这些」。
### Function Call 的工作原理（四步）
1. **定义函数**：开发者用 JSON 描述每个函数的名字、功能说明和参数，告诉 LLM 有哪些工具可用。示例：
```json
{
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "get_weather",
        "description": "获取指定城市的实时天气",
        "parameters": {
          "type": "object",
          "properties": {
            "city": { "type": "string", "description": "城市名称，比如：上海" }
          },
          "required": ["city"]
        }
      }
    }
  ]
}
```
2. **模型判断**：LLM 分析用户意图，自行决定调用哪个函数并生成参数，如 `{"city": "上海"}`。
3. **执行函数**：**LLM 自己并不执行函数**，只输出结构化的调用指令；真正执行的是应用程序，拿到指令后实际调用 API。
4. **生成回答**：把真实数据再次发给 LLM，LLM 基于客观数据用自然语言回复。
### 为什么 Function Call 重要？
解决了两个核心问题：
- **「什么时候调用」的判断问题**：LLM 根据自然语言意图自动判断是否需要调用工具、调用哪个；
- **「传什么参数」的提取问题**：LLM 从自然语言中提取结构化参数。
**Function Call 是 Agent 能力的最底层技术基础**，没有它 Agent 无法调用工具。目前主流大模型（GPT、Claude、Gemini、Llama 等）都支持，API 格式略有差异但核心原理相同。
### Function Call 和 Agent 的关系
- Function Call 是一次性的「单步调用」；
- Agent 是「循环调用」，在循环中反复使用 Function Call，观察结果再决定下一步。
即：**Function Call 是 Agent 的「原子操作」，Agent 是 Function Call 的「高级编排」**。
## 五、MCP 是什么协议？
### Function Call 的集成困境
N 个 AI 应用对接 M 个外部服务，需要写 N × M 个定制集成，完全不可扩展；且各厂商 Function Call 格式不统一（OpenAI 用 `tool_calls`，Anthropic 用 `tool_use` content block）。
### MCP 的诞生
Anthropic 在 2024 年 11 月开源了 **MCP（Model Context Protocol，模型上下文协议）**，可理解为**「AI 界的 USB-C 接口」**：提供统一标准，让任何 AI 应用用同一种方式连接任何外部工具和数据源。
### MCP 的架构（三个角色）
- **MCP Host（宿主）**：AI 应用本身（Claude Desktop、Cursor、自研 Agent），交互的发起方；
- **MCP Client（客户端）**：住在 Host 里，负责跟 MCP Server 通信的「翻译官」；
- **MCP Server（服务端）**：对外暴露具体工具能力和数据资源（如 GitHub MCP Server 提供搜索代码、创建 Issue 等工具）。
流程：用户提问 → Host 通过 Client 发现可用工具 → AI 决定调用 → Client 向 Server 发请求 → Server 执行返回结果 → AI 生成回答。
### MCP 解决了什么问题？
- 把 **N × M 的集成问题变成 N + M**：应用实现一次 Client、服务实现一次 Server 即可自动对接；
- 工具**可发现**：应用启动时自动查询有哪些 Server、提供哪些工具、参数是什么，Agent 可在运行时动态发现新能力。
## 六、Skills 是什么？
### 定义
Skills（技能）是一种**自然语言指令文件**（通常 Markdown 格式），教 Agent「在什么场景下、按什么方法、遵循什么规范来完成特定任务」。在 Claude Code、Cursor 等工具中以 `SKILL.md` 文件形式存在。
结构：顶部 YAML 元数据声明何时激活，下面是自然语言写成的行为指令。示例：
```markdown
---
name: Code_Review_Expert
description: 当用户要求进行代码审查时，自动触发此技能。
---
# 身份设定
你是一个拥有 10 年开发经验的资深后端架构师，极其看重代码的可读性、性能和安全性。
# 审查工作流
1. 看结构：检查单一职责原则，有没有超过 100 行的超长方法。
2. 查漏洞：SQL 注入、越权访问、空指针异常风险。
3. 审性能：for 循环里查数据库？流对象没有及时 close？
4. 给方案：针对每个问题给出具体修改建议并附优化代码。
# 输出规范
语气专业、直接，输出 Markdown 格式审查报告。
```
类比：MCP 给了 Agent 一个装满工具的**厨房**（解决「能做什么」），Skills 是**菜谱**（解决「该怎么做」）。
### Skills 的工作方式
Agent 启动时扫描可用 Skills 列表；用户请求来了判断有无匹配 Skill，有则加载到上下文中，按指令思考和行动。
关键点：**Skills 不只是告诉 Agent 怎么想，还能指导怎么做**——可通过 `allowed-tools` 声明需用的工具（Bash、Read、Edit 等），可打包可执行脚本，可指导 Agent 调用 MCP 工具或发起 Function Call。
本质：**Skills = 知识 + 行为指令**，加载到上下文中改变 Agent 的思考和行为方式，同时可驱动外部操作，相当于给 Agent 临时注入专业经验。
### Skills 的价值
将专业知识和最佳实践编码成可复用模块（代码审查流程、SQL 优化经验、客服话术规范等），可共享复用，团队所有 Agent 都能用。
## 七、Function Call、MCP、Skills 有什么区别？
### 统一的比喻（Agent = 新员工）
- **Function Call = 打电话的能力**：最基础，没有它无法与外部互动；
- **MCP = 公司的通讯录和电话系统**：统一管理所有外部联系方式，新增联系人全员可用；
- **Skills = 岗位培训手册**：教做事的方法、流程和规范。
### 三者的本质区别
| 维度 | Function Call | MCP | Skills |
|:---|:---|:---|:---|
| 解决的问题 | LLM 怎么跟外部函数交互 | 怎么用统一标准管理大量工具 | Agent 怎么获得领域专业知识 |
| 运行位置 | 函数在你的应用程序中执行 | 工具在外部 MCP Server 中执行 | 在 Agent 上下文窗口内生效 |
| 技术本质 | API 协议（结构化调用请求） | 通信标准（Client/Server 发现与调用） | 提示词扩展（自然语言行为指令） |
| 标准化程度 | 各厂商格式不统一 | 统一开放标准，跨厂商通用 | 尚无统一标准，各平台自有格式 |
### 三者的关系：分层互补
- Function Call 是**底层基础**；MCP 建立在它之上，提供标准化包装（通过 MCP 调工具，底层仍是 Function Call）；
- Skills 在不同维度工作：不参与工具调用过程，而是指导「什么时候调用、用什么策略」。
做饭总结：Function Call 是「会使用厨具的能力」，MCP 是「设备齐全的标准化厨房」，Skills 是「菜谱和厨艺经验」。
## 八、什么是 A2A 协议？
### 为什么需要 A2A？
多个 Agent（不同团队开发、不同框架）需要互相协作时，它们之间怎么通信？MCP 解决不了——MCP 处理的是 Agent 与**工具**之间的交互，Agent 与 Agent 之间的协作需要新协议。
### A2A 是什么？
**A2A（Agent-to-Agent Protocol）**是 Google 在 2025 年 4 月 Google Cloud Next 大会上发布的开放协议，联合 50+ 合作伙伴（Atlassian、Salesforce、SAP、MongoDB、LangChain 等），定义了标准让不同 AI Agent 能**互相发现、互相通信、互相委派任务**，与框架和平台无关。
### A2A 的核心概念
1. **Agent Card（智能体名片）**：JSON 格式的「名片」，描述身份、能力、擅长领域、交互方式、认证要求等，其他 Agent 通过名片了解「它会什么、能请它帮什么忙」；
2. **任务（Task）**：所有协作围绕任务展开，Client Agent（发起方）创建任务发给 Remote Agent（执行方），任务有完整生命周期（创建→处理中→完成/失败）；
3. **消息和制品（Message & Artifact）**：消息用于过程中沟通，制品用于传递最终结果（如分析报告）。
### A2A 和 MCP 的关系
**MCP 是「竖向」的，处理 Agent 到工具的连接；A2A 是「横向」的，处理 Agent 到 Agent 的协作。**
两者互补、可共同使用：编排 Agent 通过 A2A 把任务委派给专业 Agent，每个专业 Agent 内部通过 MCP 连接自己的工具。
### A2A 的技术特点
- 完全基于现有 Web 标准：HTTP 传输、JSON 消息格式、SSE 实时流式通信；
- 支持**异步和长时间运行的任务**（状态查询、进度更新、断线重连）；
- **模态无关**：可交换文本、音频、视频、图像、结构化数据等。
### A2A 的生态现状
截至 2026 年初仍处于早期阶段，不如 MCP 已成事实标准，但有 Google 和 50+ 伙伴推动，且填补了 MCP 不处理的空白（Agent 间协作）。
## 九、全文总结
- **LLM**：强大的文本生成引擎，有「不能做事、没有记忆、不会用工具、不会规划」四大弊端；
- **Agent**：在 LLM 基础上加入工具、记忆、规划能力，从「回答问题」进化到「完成任务」；
- **Workflow vs Agent**：区别在于「谁在控制流程」，代码控制 vs LLM 自主决策；
- **工作模式**：ReAct 边想边做、Plan-and-Execute 先想后做、Reflection 做完检查、Multi-Agent 团队协作；
- **Function Call**：让 LLM 能调用外部函数的基础能力（能力层）；
- **MCP**：统一 Agent 与工具连接的标准协议，「AI 界的 USB-C」（连接层）；
- **Skills**：教 Agent 做事方法的知识层，解决「怎么做」（知识层）；
- **A2A**：解决 Agent 之间互相发现和协作，与 MCP 形成「横向+竖向」的完整协议生态。
协议分层格局：**Function Call 提供底层调用能力，MCP 标准化 Agent 与工具的连接，A2A 标准化 Agent 与 Agent 的协作**，三层各司其职、互补共存。
