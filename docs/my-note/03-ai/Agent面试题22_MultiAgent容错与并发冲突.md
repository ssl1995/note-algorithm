# Agent 面试题 22：Multi-Agent 系统如何处理子 Agent 超时、失联和并发修改冲突？
> 来源：https://xiaolinnote.com/ai/agent/22_multi_agent_resilience.html
## 🎯 核心考点一句话
不是考超时重试，而是考**能否让一群 Agent 在部分失败和并发执行时，仍然只把正确结果提交一次**：通信问题与一致性问题分开、租约+fencing token 防双写、重试绑定幂等+checkpoint、并发修改靠所有权+乐观并发+唯一 Integrator 验收。
## 💡 简要回答（面试可直接背）
- 心跳中断只说明协调器看不到子 Agent，不能证明它已停止；任务分配带**租约+递增执行代次（generation/fencing token）**，子 Agent 定期续租；租约过期才能接管，旧执行者恢复后带旧代次提交会被存储层直接拒绝；
- 接管不从零重跑：读最近 checkpoint（已完成步骤、产物版本、外部副作用状态）；重试用稳定任务 ID+步骤 ID+幂等键；结果未知的写操作**先查外部系统再决定继续、补偿还是人工确认**；连续失败支持换模型/换工具/拆小任务/人工接管；
- 并发改同一仓库：规划阶段先按任务/文件所有权减少写集合重叠；各 Agent 在独立 worktree/branch 工作；普通文件乐观并发、少数热点文件带租约短锁；**只有 Integrator 有最终提交权**，按依赖顺序合并并跑静态检查+单测+集成测试；文本冲突或语义冲突（Git 合得动但接口已不一致）交回对应 Agent 修正。
## 📝 详细解析
### 超时、失联、失败不是一回事
协调器十分钟没收到回复，有三种可能：模型调用卡死、进程退出、仍在执行但心跳没传回来。前两种是执行失败，第三种是通信故障。直接派新 Agent 从头执行 → 旧 Agent 恢复后也提交 → 同一任务两个执行者 → 重复写入/结果覆盖/重复扣款。
**执行状态与通信状态分开记录**：执行状态 `PENDING → RUNNING → SUCCEEDED`；通信状态记录最近心跳、租约到期时间、进程健康。不能混成一个 `online` 字段。
### 租约 + fencing token 比永久锁更适合故障接管
- 租约包含 `task_id`、`worker_id`、`lease_expire_at`、递增 `generation`；子 Agent 定期心跳续租；
- 一两次心跳未到只标记可疑，超租约+宽限期才放回队列，新执行者拿更大 generation；
- 旧 Agent 恢复后带 `generation=7` 提交，任务已是 `generation=8`，**存储层直接拒绝旧写入**（fencing token = 会失效的排队号码）；
- 超时要分层：模型首字延迟、单次工具超时、子任务总预算、租约时长各是不同边界；软超时用于取消动作/换路径，硬预算终止任务并升级。
### 重试必须和幂等、checkpoint 一起设计
- 幂等键 = `task_id + step_id + operation_type`，同一逻辑动作不管谁接管都携带同一个键；下游保存键和首次结果，重复请求返回原结果；
- checkpoint 记录：已完成步骤、输入版本、产物位置、工具调用编号、外部资源 ID、写操作状态（`planned`/`succeeded`/`failed`/`unknown`）；
- 接管策略：`succeeded` 跳过、明确 `failed` 预算内重试、**`unknown` 先按业务键查外部系统**，查不了就暂停转人工；
- 误区：加幂等键 ≠ 严格「只执行一次」；现实目标是允许至少一次投递，靠幂等+唯一约束+结果查询+补偿收敛到业务可接受的一次。
### 接管策略
- 读最近已提交 checkpoint，接管上下文包含原目标、验收标准、已完成产物、当前阻塞、已尝试路径、剩余预算；
- 降级路径：工具限流→同能力 Agent 退避继续；模型多次失败→换更强模型或拆小步骤；外部依赖不可用→返回部分结果并明确缺失项；高风险动作（付款/删除/发布）且历史结果无法确认→停止自动接管转人工；
- **接管要限次数**：坏任务被十个 Agent 轮流接走是把死循环扩大；记录接管次数、连续失败类型、剩余预算，超阈值进降级/人工并保留完整 Trace。
### 并发修改：先别急着上锁
1. **规划期减少重叠**：Planner 拆任务时标出预计修改的模块/文件/接口，声明任务所有权与文件所有权；公共类型、依赖清单、全局配置等热点资源默认一个明确 Owner；
   - 任务所有权 = 谁对子任务最终结果负责；文件所有权 = 当前阶段谁可以提交这个文件；同一版本不能没有明确写入者；
2. **独立工作区**：各 Agent 在独立 Git worktree/branch 工作，记录 `base_commit`；半成品不污染别人上下文，失败任务不留垃圾；
3. **乐观并发为主**：提交时比较 `base_commit` 与目标分支，相关文件没变就尝试合并，变了就基于新版本重放补丁或交回原 Agent 修正；
4. **短锁为辅**：全局路由表、数据库迁移序号、依赖锁文件等高频热点用带租约短锁，**锁只保护提交阶段**，不覆盖思考/生成/局部测试过程；
5. **语义冲突 Git 发现不了**：A 改接口签名、B 按旧签名调用，文本可自动合并但程序已坏——接口契约、Schema、测试、静态分析是第二道防线。
### 必须有唯一最终提交者
- 只有 Integrator/Orchestrator 拥有最终提交权，其他 Agent 只产出候选分支、补丁和验证证据；
- Integrator 按任务 DAG 和接口依赖定合并顺序（公共类型→服务端接口→调用方→测试），每次合并后跑格式/静态检查+受影响单测，全部合并后跑集成测试；
- 文本冲突：保留两边意图、最新基线和冲突文件，让负责模块的 Agent 重新生成补丁，**不让模型随意选一边**；合并成功但测试失败：把失败用例、Trace、接口变更交回；验收通过才生成唯一最终提交。
## 🎯 面试总结
- 第一层：分清执行失败与通信故障，状态分开记录；
- 第二层：租约 + 递增 generation（fencing token）解决「旧执行者复活双写」，永久锁 TTL 挡不住已进临界区的旧进程；
- 第三层：重试三件套——checkpoint、幂等键、unknown 先查询；现实目标是「至少一次投递 + 收敛到一次副作用」；
- 第四层：并发修改靠规划期所有权划分 + worktree 隔离 + 乐观并发 + 热点短锁 + 唯一 Integrator 验收；Git 文本合并不等于逻辑正确，语义冲突靠契约和测试兜底。
