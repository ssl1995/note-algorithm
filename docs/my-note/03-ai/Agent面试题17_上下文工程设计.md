# Agent 面试题 17：Agent 的上下文工程（Context Engineering）怎么设计？
> 来源：https://xiaolinnote.com/ai/agent/17_context_engineering.html
## 🎯 核心考点一句话
上下文工程 ≠ Prompt 拼接 ≠ 记忆压缩；它考的是 Agent **每一步模型调用前，能否动态装配出一份「可信、相关、够用」的工作现场**——选什么、怎么排序、怎么隔离、预算怎么分。
## 💡 简要回答（面试可直接背）
- 把上下文工程设计成**运行时装配流程**，而不是把所有信息长期堆在一个 Prompt 里；
- 每次模型调用前，根据当前子任务从指令、任务状态、短期对话、长期 Memory、工具定义与结果、RAG 证据中**挑选本轮需要的内容**，再做优先级排序、来源隔离和 Token 分配；
- **先预留输出空间**，再给各类上下文设预算和不可丢失项；超预算时按「去重 → 裁低相关证据和无关工具 → 结构化状态替代冗长过程 → 压缩旧历史」顺序降载；
- 执行后把状态增量写回外部状态库，**每一步都重新装配**，而不是让模型靠聊天记录记住一切。
## 📝 详细解析
### 上下文的四层组成（各自职责不同）
| 层 | 内容 | 职责 |
|:---|:---|:---|
| 指令层 | System / Developer / User 指令 | 决定行为边界（要做什么、不能做什么），高优先级不可被低优先级覆盖 |
| 任务状态层 | 核心目标、约束、To-Do、当前步骤、已完成项 | 决定执行位置（现在做到哪了）——最容易被忽略，却最影响多步任务连续性 |
| 对话与 Memory 层 | 近期对话 + 长期 Memory（偏好、历史决策） | 补充过去；Memory 只是候选背景，不是永远正确的事实 |
| 外部观察层 | 工具定义、工具结果、RAG 证据 | 补充能力与外部事实；内容长、质量参差，最需动态选择 |
### 筛选：先选再拼，四个维度
围绕**当前子任务**筛选，综合看：①相关性；②来源可信度；③信息新鲜度；④缺失后的风险。
- 必须保留：用户硬约束、未完成任务、刚发生的工具错误（漏掉就把任务带偏）；
- 可不注入：重复检索结果、不再影响后续的中间推理、当前不可用工具的完整定义；
- **坑：Top K 只解决「相关不相关」，解决不了「可信不可信」**——检索打分后还要做来源过滤、去重、版本判断，事实回答要保留证据来源。
### 排序：是在表达优先级，不只是排版
一般顺序：稳定权威的行为规则在前 → 用户当前目标与结构化任务状态 → 本轮工具说明 / RAG 证据 / 工具观察 → 最后明确输出要求。
- 「规则、状态、数据」必须**分区**，不能混成无边界长文本；
- 固定前缀保持稳定可命中**前缀缓存**（成本/延迟优化），但不能为缓存牺牲指令正确性。
### To-Do 的价值：把进度变成显式状态
任务状态应包含 core_intent、success_criteria、constraints、todo（id/status/evidence_ref）、open_questions；执行前看 in_progress 项，执行后写回结果与状态。用户改需求或工具结果证明原计划走不通时，要**重新评估并更新计划**，否则过期 To-Do 会把模型锚定在错误路径上。
### 隔离：防止外部数据变成指令（防注入）
- 指令区和数据区明确分开，RAG 文档/网页/邮件/工具返回值带来源、时间、权限等元数据，**只当数据处理，不能混成命令**；
- 权限校验必须由模型之外的程序执行，不能只靠 Prompt 约束；
- 当前步骤只暴露必要工具，高风险工具加外部参数校验和人工确认；子 Agent 只拿自己的子任务和局部状态，不默认继承主 Agent 全部历史。
### Token 预算：装配前分，不是超长后截断
- 第一步先预留输出 Token 和安全余量，剩下的才分给输入；
- 预算随任务阶段动态调整（事实问答多给 RAG，工具执行重任务状态，会话恢复重已确认约束），不要共用一个固定模板；
- 不可丢失项：用户硬约束、当前目标、安全规则、未完成状态；装不下时宁可分步检索或向用户确认，**不要静默截掉关键要求**。
### 闭环：每一步都重新装配
链路：确定当前步骤 → 读取最新指令和任务状态 → 按需召回 Memory/RAG/工具 → 过滤冲突和低质量内容 → 分配 Token 并分区渲染 → 调用模型 → 状态变化和证据引用写回。
评估指标：约束遵循率、关键事实召回率、工具选择正确率、任务完成率、引用忠实度、多轮续做成功率，配合 Trace 记录每轮注入内容。
### 概念边界（高频追问）
| 概念 | 解决的问题 |
|:---|:---|
| Prompt Engineering | 怎么说：指令和模板怎么写清楚 |
| Memory | 信息怎么长期保存和召回（仓库） |
| 记忆压缩 | 内容太长怎么缩（一种手段） |
| RAG | 证据怎么找回来（找资料的机制） |
| Context Engineering | 这一轮模型到底该看到什么（工作台装配，动态贯穿整个运行过程） |
## 🎯 面试总结
- 不能说「把历史拼进 Prompt」，也不能一上来只聊滑动窗口和摘要；
- 完整思路：先讲四层组成（指令定边界、任务状态定位置、Memory 补过去、RAG/工具补事实）→ 再讲工程设计（围绕子任务选择、四维排序、指令与数据隔离、预算预分配、每步重新装配）→ 最后划清与 Prompt Engineering / Memory / 压缩 / RAG 的概念边界；
- 讲到这个层次，面试官才能判断你做的是能持续执行多步任务的 Agent，而不是聊天机器人。
