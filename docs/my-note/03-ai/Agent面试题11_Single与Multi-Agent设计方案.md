# Agent 面试题 11：说说 Single-Agent 和 Multi-Agent 的设计方案？
> 来源：https://xiaolinnote.com/ai/agent/11_single_multi.html
## 🎯 核心考点一句话
选型有清晰决策逻辑：**默认 Single-Agent，只有命中「context 撑爆 / 需要专业分工 / 有子任务可并行」三类场景才上 Multi-Agent；而 Multi-Agent 生产环境几乎只选中心化的 Orchestrator 模式**（可控、可追踪、好排查），去中心化只停留在学术研究。
## 💡 简要回答（面试可直接背）
- **Single-Agent** 适合任务流程清晰、复杂度适中的场景：实现简单、好维护、链路透明；
- **Multi-Agent** 适合需要专业分工、任务量大或需要并行执行的复杂场景；
- Multi-Agent 有两种拓扑：**中心化 Orchestrator 模式**（主 Agent 统一调度 Worker）和**去中心化 Peer-to-Peer 模式**（Agent 间直接通信）；
- 工程里用**中心化**更多：好控制、好调试，出问题链路清晰。
## 📝 详细解析
### Single-Agent
- 本质：一个 LLM + 一套工具跑决策循环（判断下一步 → 调工具 → 拿结果 → 再判断，直到完成）；
- 最大优势不只是「架构简单」，更核心的是**整条任务链路完全在掌控之内**：所有逻辑在一个地方写清楚，链路短、好排查；
- 类比：一个人独立完成「写一篇博客」，沟通成本为零，单人反而更高效。
**Single-Agent 力不从心的三类场景（= Multi-Agent 的真实价值点）**：
1. 任务太长、信息量太大，**context 撑爆**，Agent 开始遗忘；
2. 不同步骤需要**完全不同的专业能力**，塞进一个 Agent 每件事都不专注；
3. 任务中有多个**独立子任务可并行**，单 Agent 只能一个个来。
⚠️ 不属于这三类就用 Single-Agent，不要为「用新技术」强行引入 Multi-Agent——系统变复杂、难维护，却没有对应收益。
### Multi-Agent 中心化方案：Orchestrator 模式
- **Orchestrator**（交响乐指挥，可理解为「总调度员/项目经理」）：系统里最特殊的 Agent，**不做任何具体工作**，只负责三件事——读懂大目标并拆成子任务；判断每个子任务交给哪个 Worker；收集 Worker 产出拼成最终答案。
- **Orchestrator 的三种变体（按复杂度递增）**：
  1. **静态路由（Static Router）**：拆分和分配规则预定义（「代码任务给 Coder，搜索任务给 Researcher」），简单可预测；
  2. **动态规划（Dynamic Planner）**：Orchestrator 本身是 LLM，根据输入动态生成计划、执行中可调整——**大多数场景用它就够了**；
  3. **自适应编排（Adaptive Orchestration）**：根据 Worker 执行结果实时调整后续计划（搜回信息不够就追加一轮搜索），更强大但调试复杂度高很多。
- **Worker Agent** 是「执行者」：不关注整体任务、不知道其他 Worker 在做什么，拿到自己那部分指令做完返回即退出，**context 干净**，只装与职责相关的信息。
- 实例「写 AI 行业竞品分析」最大好处：**每个环节出问题能精准定位**——内容不准找 Researcher、分析逻辑有问题找 Analyst、格式不符找 Writer，顺着 Orchestrator 调度记录就能追到根源。
### 去中心化方案：为什么「听起来灵活」却没人用
思路：没有总调度，Agent 通过共享消息队列/状态空间自行协商、直接通信。实际工程问题（三个 Agent 场景：A、B 各自搜索，C 汇总，无人统筹）：
1. **任务分配没有协调**：没人告诉 A、B 各搜什么范围 → 大量重复工作；
2. **执行顺序没有保证**：没人告诉 C「A、B 什么时候算搜完」→ 不知等多久、是否漏了结果；
3. **失败没有感知**：A 中途出错没人收到通知 → 汇总出不完整结果，系统甚至不知道出了问题；
4. **没有人确认「任务整体完成」**。
类比没有项目经理的团队：每个人都能干，但没人协调时间节点和接口，交付物互不兼容且没人知道整体进度。
✅ 结论：去中心化更多停留在**学术研究**（探索「AI 系统能否自主协调」），生产环境**几乎所有正经项目都选 Orchestrator 模式**——可控、可追踪、出问题能排查，这才是工程真正需要的。
### 选型决策：两个问题搞定
1. **你的任务 Single-Agent 能搞定吗？** 流程明确、不太长、不需要多种专业分工 → 就用 Single-Agent，不为「显得高级」引入 Multi-Agent；
2. **你能接受系统行为不可控的风险吗？** 生产环境答案几乎一定是「不能」→ 用 Orchestrator 模式。
**🔥 渐进式演进策略（实用加分项）**：先用 Single-Agent 跑起来，发现某环节确实成为瓶颈（context 常撑满、某类子任务质量不行）再把那个环节拆出来给专门的 Worker Agent。不要一上来设计五六个 Agent 的复杂系统——你可能连真正的瓶颈在哪都还没搞清楚。
**行业趋势：A2A 协议**（Agent-to-Agent，Google 2025 年 4 月提出的开放标准）：解决不同团队/框架开发的 Agent 之间如何通信协作（类似微服务思路）；2025 年 6 月捐给 Linux 基金会，IBM 的 ACP 已并入。目前仍较早期，跨框架即插即用未完全成熟，但长远看会深刻改变 Multi-Agent 的构建方式。
### 三种方案对比表
| 维度 | Single-Agent | Multi-Agent（中心化） | Multi-Agent（去中心化） |
|:---|:---|:---|:---|
| 架构复杂度 | 低 | 中 | 高 |
| Context 压力 | 全压在一个 Agent | 各 Agent 独立管理，Orchestrator 只维护高层状态 | 各 Agent 独立管理，但需额外共享协调状态 |
| 专业能力 | 泛才，什么都做 | 专才分工，各有专责 | 专才分工，各有专责 |
| 并行能力 | 不支持 | 支持子任务并行 | 支持并行 |
| 可控性 | 高 | 高，Orchestrator 统管 | 低，难以统一调度 |
| 调试难度 | 容易 | 中，按调度链路追踪 | 难，行为不可预测 |
| 工程实用性 | 高 | 高 | 低，主要用于学术研究 |
| 适用场景 | 任务清晰、复杂度适中 | 需要分工或并行的复杂任务 | 学术探索场景 |
## ⚠️ 面试常见踩雷点
1. **选型标准只说「任务复杂就用 Multi-Agent」**：要说出三类具体场景（context 撑爆、专业分工、子任务可并行），不属于这三类就用 Single-Agent，盲目引入只增复杂度没有收益；
2. **漏掉架构拓扑**：要主动提中心化/去中心化两种，并明确工程里几乎都选 Orchestrator 中心化模式（可控、可追踪、顺调度链路排查）；
3. **觉得去中心化「更灵活更好」**：要说清它的实际工程问题——任务分配没协调、执行顺序没保证、失败没有感知，这是它在生产环境不可用的根本原因。
## ✅ 答题 checklist
- [ ] 给出明确选型标准：三类场景才上 Multi-Agent，否则 Single-Agent 够用；
- [ ] 讲清 Orchestrator 职责（拆任务/派任务/收结果）和三种变体（静态路由/动态规划/自适应编排），Worker context 隔离干净；
- [ ] 说明去中心化的四大工程问题，以及生产环境几乎只选中心化的原因；
- [ ] 加分项：渐进式演进策略（先 Single 跑起来再拆瓶颈）、A2A 协议趋势。
