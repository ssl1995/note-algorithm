# Agent 面试题 18：多轮对话状态如何管理？如何防跑偏并支持中断恢复？
> 来源：https://xiaolinnote.com/ai/agent/18_session_state.html
## 🎯 核心考点一句话
考的是**怎样把一段自然语言对话变成可控、可追踪、可安全恢复的任务链**——「聊天记录存在哪」只是最基础的一层；防跑偏 ≠ 不许用户改需求，中断恢复必须讲清**幂等与外部副作用核对**。
## 💡 简要回答（面试可直接背）
- 信息分四类管理：对话历史（原话）、业务状态（已确认实体与约束）、任务状态（目标/步骤/工具进度）、长期记忆（跨任务偏好）；
- 显式维护 `core_intent`、`current_subtask`、`pending_tools`、`completed_steps`、`context_snapshot`；每轮先判断用户输入是补充、纠错、澄清回复还是切换任务；
- 用状态机控制合法流转（如 `PLANNING → EXECUTING → WAITING_USER → CHECKING → DONE`），自然语言历史负责理解，状态机负责执行；
- 中断恢复：`session_id`/`thread_id` 隔离会话 + `task_id` 标识任务 + 关键步骤 checkpoint；恢复时加载最近已提交状态并核对未决工具调用，**外部写操作必须带稳定幂等键**。
## 📝 详细解析
### 四类信息为什么要分开
| 信息类型 | 主要内容 | 生命周期 | 用途 |
|:---|:---|:---|:---|
| 对话历史 | 用户原话、模型回复、工具返回 | 当前会话 | 还原语义、指代、语气、决策原因 |
| 业务状态 | 日期、金额、目标群等已确认事实 | 当前业务任务 | 给业务规则和工具提供可信参数 |
| 任务状态 | 核心目标、当前子任务、待办、步骤状态 | 一次任务执行 | 控制流程、重试、暂停与恢复 |
| 长期记忆 | 用户偏好、可复用经验 | 跨会话 | 个性化与经验召回 |
同一句话放错位置后果完全不同：「这次报告用英文」是当前任务约束，不该直接写成「用户永远偏好英文」的长期记忆；「订单创建成功」不能只躺在聊天历史里，还要更新步骤状态并记录订单号供恢复核对。
**与 Memory 题的区别**：Memory 关心跨任务保留与召回；状态管理关心正在执行的这件事走到哪、下一步是否合法、故障后如何接着走。
### 任务状态核心字段
| 字段 | 记录什么 | 更新原则 |
|:---|:---|:---|
| `core_intent` | 归一化的核心目标、约束、完成标准 | 模型不能自行覆盖；用户明确改需求时版本化更新 |
| `current_subtask` | 当前子任务 | 步骤开始/切换时更新 |
| `pending_tools` | 未完成工具调用（编号、参数摘要、状态） | 先登记再执行，拿到结果改成功/失败/未知 |
| `completed_steps` | 已完成步骤的结论、证据引用 | 只记可复用结论，不复制整段原始日志 |
| `context_snapshot` | 当前有效实体（时间、地点、订单号等） | 校验后合并，保留来源与版本 |
辅助字段：`session_id`/`thread_id`（连续交互）、`task_id`（会话中的具体任务，一个会话可能有多个任务）、`state_version`（乐观锁防并发覆盖）。
### 每来一条新消息，状态怎么更新
把新输入分四类：补充约束（更新 snapshot）、纠错（覆盖槽位并让依赖旧值的步骤失效）、澄清回复（解除 WAITING_USER）、新任务（暂停旧 task_id 创建新任务）。
- **误区纠正**：`core_intent` 的锁定不是死守第一句话——先把需求归一化为目标/约束/验收条件并让用户确认，之后禁止模型静默改写，用户明确修改时生成新意图版本并记录来源；
- 意图锚点是预警信号不是裁判：置信度不够就问一句，不要擅自改状态。
### 状态机和自然语言历史，谁说了算
- 自然语言历史负责**理解**（「还是按上周那个风格来」需要结合上下文）；
- 状态机负责**执行**：当前是 `WAITING_CONFIRMATION` 时即使模型建议调用发送工具也应拒绝；付款/发送/删除等高风险动作的合法状态转换由确定性代码校验，不能只靠 Prompt；
- 模型可以提出「更新哪些字段、下一步去哪」，但输出必须经 Schema 校验、权限校验和状态转换校验，**最终提交状态的是编排层**。
### 防跑偏的三道防线
1. 始终保留结构化 `core_intent`（含最终产物、约束、完成标准），规划和检查前与 `current_subtask` 一起提供给模型；
2. 进度核对：每个关键步骤问「是否推进了核心目标、下一步是否仍来自未完成计划」；连续弱相关或丢验收条件就重新规划或人工澄清；
3. 保留事实来源和状态版本：`context_snapshot` 关键字段带来源/置信度/更新时间，用户纠正后让依赖旧值的步骤失效。
固定每五轮摘要、超二十轮强制重对齐可作为工程策略，但更合理的触发条件是 Token 预算、任务阶段变化、关键状态更新和偏航风险。
### 中断恢复五步走
1. 可信身份校验 `session_id`，定位 `task_id`（防读到别人的任务）；
2. 加载最近一次完整提交的 checkpoint，校验状态版本和工作流版本；
3. 看 `pending_tools`：`succeeded` 跳过、`failed` 按策略重试、**`unknown` 先去外部系统核对**（响应丢失≠没执行，直接重试会重复发消息/重复扣款）；
4. 重新组装最小必要上下文（规则 + 核心意图 + 当前状态 + 近期对话 + 关键工具结果 + 必要长期记忆）；
5. 从合法状态继续，记录恢复来源、次数和结果供审计。
**幂等设计**：执行前登记意图生成稳定 `operation_id`，执行后保存平台返回的 `message_id`；用稳定业务幂等键 + 外部接口按键去重；数据库用唯一约束/upsert；外部系统既不可查询也不支持幂等时，转人工确认而不是盲目重发。
### 线上细节
- 冷热分层：活跃会话放 Redis，关键 checkpoint 和审计落持久化存储；TTL 不能让等待审批的长期任务消失；
- 并发：按 `task_id` 加租约/分布式锁 + `state_version` 比较后更新；用户请求带 `request_id` 防重复提交；
- 敏感信息不进状态；大结果存外部只留摘要/哈希/引用；
- 观测指标：意图改写次数、澄清率、非法状态转换次数、恢复成功率、重复副作用次数、恢复后与不中断基线的一致性。
## 🎯 面试总结
- 不要把状态管理说成「历史消息存 Redis」：先分四类信息，再用 `core_intent` 锚定目标 + 结构化字段记录进度；
- 防跑偏不是死守第一句话：防的是模型静默改目标，用户明确修改要版本化；自然语言历史保细节、结构化状态存结论，缺一不可；
- 中断恢复必须说到 checkpoint、`task_id`、幂等键和「unknown 状态先核对再决定重试」，绝不能看到步骤没成功就直接重跑。
