# Agent 面试题 16：如何设计多 Agent 的协作与动态切换机制？
> 来源：https://xiaolinnote.com/ai/agent/16_collab.html
## 🎯 核心考点一句话
协作与切换是**两个独立的设计问题**：协作（信息怎么传）在**消息传递 vs 共享状态**之间取舍，切换（下一步叫谁）在**静态路由 vs 动态路由**之间取舍——最能体现工程经验的答案是**混合策略：主流程静态路由保底，边缘情况才交给 LLM 动态决策**。
## 💡 简要回答（面试可直接背）
- **协作靠两件事**：①消息传递——Agent 做完把结果发到消息队列，下游订阅取用，核心是**解耦**；②共享状态——所有 Agent 读写同一个状态对象，核心是**直接**（LangGraph 就是这个思路）；
- **动态切换靠 Orchestrator 做路由**：①静态路由——提前写死规则「任务类型 A 就找 Agent X」；②动态路由——把上下文交给 LLM 实时判断该叫谁；
- **实践是两种混用**：主流程用静态路由保证稳定可预测，边缘情况才交给 LLM 动态判断兜底。
## 📝 详细解析
### 多 Agent 协作的三大模式（全局视角）
1. **流水线模式**：Agent 按固定顺序依次执行，前一个完成后交给下一个；
2. **层级模式**：Orchestrator（指挥者）分配任务、收集结果，其他 Agent 各自执行子任务；
3. **协商模式**：无严格上下级，多个 Agent 通过沟通、辩论达成一致。
三种模式不互斥，复杂系统常混合使用。
### 协作机制：消息传递 vs 共享状态
| 维度 | 消息传递（发邮件） | 共享状态（共享白板） |
|:---|:---|:---|
| 工作方式 | 结果发到消息队列，下游 Agent 订阅取用 | 所有 Agent 读写同一个状态对象 |
| 核心优势 | **解耦**：发送方不知道谁在接收 | **直接**：前一步写入后一步直接读 |
| 代价 | 需要消息中间件，部署成本稍高 | 设计不好容易互相覆盖、读到脏数据 |
| 典型代表 | 消息中间件方案 | **LangGraph**：贯穿所有 Agent 的 State，节点返回增量更新，框架合并 |
| 适用场景 | Agent 需独立并行、互不感知对方 | 流水线型任务、步骤间前后依赖明确 |
**🔥 共享状态的设计要点（最易出 bug 的地方）**：
1. **状态分层**：全局状态（原始请求、任务进展、最终输出，所有 Agent 共享）+ 局部状态（各 Agent 的中间结果，如候选文档列表、草稿代码，不外泄、避免信息污染）；
2. **写入规则：只追加不覆盖**——每个 Agent 追加增量而非修改已有字段（LangGraph 的 State 更新机制即如此），杜绝互相覆盖；
3. **错误状态也要写入**：Agent 执行失败的错误信息必须入状态而不是悄悄吞掉，后续 Agent/Orchestrator 才能据此跳过、换 Agent 重试或终止任务。
### 切换机制：静态路由 vs 动态路由
「切换」= 决定下一步把任务交给哪个 Agent，决策动作叫**路由**，由 **Orchestrator** 负责。
| 维度 | 静态路由 | 动态路由 |
|:---|:---|:---|
| 决策方式 | 规则提前写死（含「搜索」→ Researcher；找不到规则回 Orchestrator 兜底） | 把任务状态+可用 Agent 列表交给 LLM 判断 |
| 优点 | 效率高、可预测、好调试 | 灵活，能处理未预设计的边缘路径 |
| 缺点 | 覆盖不了没预料到的情况 | 每次路由多一次 LLM 调用（延迟+成本）；偶尔路由错，行为不可预测 |
```python
def dynamic_route(task_context: str, available_agents: list[str]) -> str:
    """让 LLM 根据当前上下文决定下一步调用哪个 Agent"""
    prompt = f"""当前任务状态：
{task_context}
可用的 Agent：
{chr(10).join(f'- {agent}' for agent in available_agents)}
请根据当前进展，判断下一步应该交给哪个 Agent 来执行。
只返回 Agent 名称，不需要解释。"""
    response = client.chat.completions.create(
        model="gpt-4",
        messages=[{"role": "user", "content": prompt}]
    )
    selected = response.choices[0].message.content.strip()
    return selected  # 返回选中的 Agent 名称
```
- 动态路由本质是**让 LLM 做一次分类决策**；生产环境要加保护措施：**校验返回的 Agent 名是否在可用列表、设默认 fallback Agent、记录路由日志**便于分析。
### Handoff 模式：去中心化的「接力棒」
- 思路：不需要中央 Orchestrator，由**当前执行的 Agent 自己决定把任务交给谁**（类比接力赛，跑完自己那棒直接递给下一人）；OpenAI **Swarm** 框架演示推广了这个模式（注意：Swarm 是教育/实验性框架，非生产级）；
- ✅ 优点：每个 Agent 最清楚自己的任务边界，交接判断往往比外部 Orchestrator 更准；无中央节点瓶颈，扩展性好；
- ⚠️ 缺点：**没有全局视角**，A→B→C→A 可能形成交接死循环；
- 🔥 必备防护：**设计好每个 Agent 的职责边界 + 防循环机制**（记录任务经过的 Agent 链，重复经过同一 Agent 就强制终止）。
### 工程实践：怎么组合使用
- **🔥 最稳健的答法——混合路由**：主流程用静态路由把确定性切换写成规则「保底」，只在无匹配规则的边缘情况交给 LLM 动态决策「兜住异常」，两者互补；
- **Handoff 适用边界**：Agent 数量少、职责边界清晰、输入输出接口明确时用 Handoff 更简洁；Agent 多、任务流向复杂时用 Orchestrator 统一调度；
- **通信方式同理**：清晰流水线、前后依赖明确 → 共享状态；多 Agent 独立并行、互不感知 → 消息传递。
## ⚠️ 面试常见踩雷点
1. **把协作笼统说成「流水线传结果」**：没说清消息传递（解耦）与共享状态（直接）的本质区别和选型依据（看 Agent 间依赖强弱）；
2. **把切换说成「全靠 LLM 动态决策」**：忽略了每次路由多一次 LLM 调用、路由可能出错、系统行为不可预测的代价；
3. **不知道混合策略**：说不出「静态路由保底 + 动态路由兜异常」这个最能体现工程经验的答案；
4. **用 Handoff 不设防循环**：交接链 A→B→C→A 死循环是典型坑。
