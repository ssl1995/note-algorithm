# Agent 面试题 19：如何评估一个 Agent 的效果？评测集和指标怎么设计？
> 来源：https://xiaolinnote.com/ai/agent/19_evaluation.html
## 🎯 核心考点一句话
Agent 评测不能只盯最后一句话——要拆到「**有没有把事做对**」：分层评测 + 可验证的外部状态作为成功信号 + **安全约束是硬门禁而非加权项** + 线上 Badcase 回流闭环。
## 💡 简要回答（面试可直接背）
- 分四层评估：**工具层**（该不该调、选对没、参数对不对）、**单步与轨迹层**（决策合理性、漏步骤/重复调用/越权）、**端到端层**（任务是否真完成、外部环境状态是否达标）、**线上层**（成功率、接管率、延迟、成本、安全事件）；
- 评测集来自真实请求、历史 Badcase、边界场景、对抗样本；每条样本保存目标状态、允许/禁止动作、关键检查点和评分规则，**多正确路径的任务不强制轨迹逐步一致**；
- 评分：确定性检查（Schema、数据库状态、单测、权限规则）优先 → 开放式质量交人工 + LLM-as-a-Judge（需人工校准裁判）；
- 安全和关键业务约束设为**发布硬门禁**，其余指标按切片与基线比较；上线后 Trace + 用户反馈回流 Badcase 到离线集，形成持续回归闭环。
## 📝 详细解析
### 为什么只看最终答案会被骗
退款 Agent 回复「退款已完成」有三种可能：真按规则完成 / 没调接口只是编了一句 / 完成了但没核验身份。文字可以很像，产品结果和风险完全不同。**最可信的成功信号是可验证的外部结果**（订单状态真的变成已退款、代码真的通过测试），而不是 Agent 自称完成。
### 四层评测指标表
| 层级 | 核心问题 | 常用指标 |
|:---|:---|:---|
| 工具层 | 工具和参数可靠吗 | 工具选择准确率、参数 Schema 通过率、参数语义正确率、执行成功率、幂等检查 |
| 单步与轨迹层 | 决策过程合理吗 | 必需步骤覆盖率、禁止动作触发率、重复调用率、轨迹冗余、约束遵循率 |
| 端到端任务层 | 事情真做成了吗 | 任务完成率、阶段目标完成度、结果正确性、多次运行稳定性（pass^k） |
| 线上业务层 | 用户和业务受益吗 | 解决率、人工接管率、延迟分位数、每次成功任务成本、安全事件率 |
要点：
- 工具层先测工具本身（确定性代码），再测模型的工具决策；**Schema 合法 ≠ 业务含义正确**；
- 轨迹层不给所有任务准备「标准轨迹」做完全匹配，而是定义三类约束：必须出现的步骤、禁止出现的步骤、有先后依赖的步骤，其余路径允许自由选择；效率在「成功且合规」前提下比较；
- 端到端：成功条件由业务定义，不能让 Agent 自己说成功；复杂任务拆阶段性目标（AgentBoard 思路）；同题多跑看稳定性——`pass^k`（连续多次都成功）≠ `pass@k`（多次机会一次过）；
- 安全指标单独看：未授权调用率、敏感信息泄漏率、注入成功率、审批绕过率——不能被加权平均掉。
### 评测集怎么建
一条完整样本应包含：初始环境状态、用户目标、预期最终状态、可用工具、必须/禁止动作、关键约束、评分规则、参考轨迹（可选）。
样本四来源：
1. **真实请求**：生产日志脱敏后按任务类型、难度、工具、轮数、风险分层采样；
2. **边界场景**：参数缺失、表达含糊、工具超时、空结果、长上下文；
3. **对抗与安全样本**：工具返回藏注入、越权请求、诱导绕过确认；
4. **历史 Badcase**：每种新失败模式确认原因后加入回归集。
防退化：按场景切片（核心任务/高风险/长对话/历史 Badcase），总分上涨可能只是简单题占比高；评测环境要可复现（可重置测试环境/Mock、固定初始状态、记录模型/Prompt/工具版本）。
### 三种评分手段
| 手段 | 擅长 | 注意 |
|:---|:---|:---|
| 确定性检查 | Schema、禁用工具、数据库终态、单测 | **优先使用**，快、稳、便宜，适合 CI |
| 人工评审 | 定义标准、高风险歧义、审查分歧样本 | 建清楚 Rubric，持续抽查自动评测 |
| LLM-as-a-Judge | 开放式质量（报告完整性、轨迹合理性） | 有位置偏差、篇幅偏差、自我偏好 |
降低裁判偏差：分维度评分、提供任务约束和证据、匿名化候选、成对比较交换顺序复核、用人工标注集衡量一致性、分歧样本人工复审；换裁判模型/Prompt 也要跑回归。
### 指标怎么组合成发布门禁
- **先硬门禁再看质量效率**：安全违规、越权、绕过审批、重复严重副作用的样本失败即阻止发布；
- 无行业通用门槛：先用当前线上版本建基线，按业务风险定门槛，同时看整体和关键切片；
- 比较版本时固定环境和配置、关键样本重复执行；评测报告要直接点出「哪类任务退化、哪步出错、代价增加在哪」。
### 离线到线上的闭环
定义成功标准 → 建评测集 → 分层评测 → 门禁通过后灰度 → 观察 Trace 和业务结果 → Badcase 归因 → 加入回归集 → 修复后同时跑定向集与全量集。
- Trace 要保留模型调用、工具选择、参数、结果、重试、耗时、Token、版本、最终环境状态；
- 点踩/追问/撤销/接管是代理指标不是真相；重要改动结合灰度或 A/B 实验；
- 修复后既跑定向集也跑全量回归，避免「修好这一类、弄坏另一类」。
## 🎯 面试总结
- 核心认知：Agent 在生成文字之外还在做决策和改变外部状态，最终回复不能独自证明「事做成了、过程合规」；
- 答题框架：四层评测（工具→轨迹→端到端→线上）+ 评测集四来源（真实/边界/对抗/Badcase）+ 三种评分手段（确定性优先、裁判要校准）+ 硬门禁与切片比较 + 线上回流闭环；
- 加分点：知道 `pass^k` 与 `pass@k` 的区别、知道 LLM 裁判的三类偏差、知道安全指标不能被综合分抵消。
