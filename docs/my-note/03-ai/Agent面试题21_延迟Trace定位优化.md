# Agent 面试题 21：线上 Agent 延迟明显升高时，如何通过 Trace 定位和优化？
> 来源：https://xiaolinnote.com/ai/agent/21_agent_latency_trace.html
## 🎯 核心考点一句话
排查 Agent 延迟最怕凭感觉优化：先分清 **TTFT（首 Token）还是总时延**、看 **P95/P99 而非平均值**、用同一 Trace ID 还原完整链路找**关键路径**，再对症优化——并行 Span 耗时不能相加，有依赖的步骤不能强行并行。
## 💡 简要回答（面试可直接背）
- 先确认慢的是 TTFT 还是总时延；按任务类型、模型版本、工具、租户、发布版本切分 P50/P95/P99，判断是整体变慢还是长尾；
- 用同一 Trace ID 串起网关、排队、上下文构建、检索、模型调用、工具调用、编排决策；每个环节独立 Span，记录耗时、状态、重试、输入输出规模、Token、错误类型（敏感内容不记原文）；
- 定位顺序：指标圈定异常范围 → 抽多条慢 Trace 与正常 Trace 对比 → 瀑布图找关键路径 → 下钻日志和资源指标；
- 优化对症：排队做容量与并发治理；模型从路由/上下文/输出长度/缓存入手；检索工具做连接复用/缓存/批量/安全并行；编排减少无效步骤和过度反思；改完用历史轨迹回放+灰度+分位数对比验证，同时守住成功率、质量、安全、成本。
## 📝 详细解析
### 先说清楚「慢」是什么
| 指标 | 含义 | 主要影响因素 |
|:---|:---|:---|
| TTFT | 请求发出到第一个 Token 到达 | 网关排队、上下文构建、首轮检索、模型排队、预填充 |
| 总时延 | 任务从接收到完成 | 生成速度、工具调用、Planner 决策、失败重试、反思次数、任务步数 |
- 平均值会被骗：90 个 2 秒请求 + 几个 30 秒请求，平均可接受但尾延迟用户已很难受；P50 看典型、P95/P99 看尾部；
- 比较口径要同类：按任务类型、模型与供应商、工具、地区、租户、输入/输出长度、发布版本切片，区分「系统变慢」还是「复杂任务变多」；
- 注意：**流式输出只改善用户感受到的等待，不缩短任务真正完成时间**。
### 一条 Agent Trace 的结构
- 根 Span = 整个 Agent 请求；子 Span = 网关鉴权、调度排队、上下文构建、检索、模型调用、工具调用、状态存储、结果整理；
- 同一链路共享 Trace ID，各 Span 有 Span ID 和父子关系；跨进程（远程工具、消息队列、子 Agent）要传播 Trace 上下文；异步/多上游场景用关联 ID 补充因果，但不能替代父子关系；
- Span 记录内容：模型（名称、输入/输出 Token、TTFT、结束原因）、检索（Query 类型、召回数量、各阶段耗时）、工具（名称、状态、错误类型、重试次数）、编排（当前步骤、路由结果、计划版本、累计步数）；
- **敏感数据不原样入日志**：记录长度、哈希、分类标签和脱敏摘要；采样要能保留罕见的超慢/错误请求（按错误状态、业务重要性、完成后总耗时保留高诊断价值 Trace）。
### 定位顺序不能反
1. **指标确认异常边界**：TTFT/总时延何时涨、哪个分位涨、成功率超时率是否同变；按维度切分找变化最明显的一组；与发布、模型切换、下游异常做时间重合分析；
2. **选慢 Trace**：从异常分组抽多条慢 Trace + 同类型同版本正常 Trace 对照（不能只看最慢一条）；
3. **瀑布图看关键路径**：真正决定总时延的是「请求开始到完成的关键路径」；两个并行工具各 3 秒，对总时延贡献≈3 秒不是 6 秒；Span 耗时不相加，Span 长 ≠ 根因；
4. **下钻日志与资源指标**：模型 Span 慢→区分客户端连接/供应商排队/TTFT/生成速度/输出变长；工具 Span 慢→看下游接口、连接池、数据库、重试；应用内慢→CPU/内存/线程池。
### 六类常见瓶颈的 Trace 特征
| 瓶颈 | Trace 特征 |
|:---|:---|
| 排队 | 调度队列等待变长（突发流量、并发上限、线程池耗尽、租户争抢、下游限流）；无独立 queue Span 时排队时间易被算进模型耗时甩错锅 |
| 模型调用 | 拆开看网络连接/服务端等待/TTFT/持续生成；TTFT 涨=排队或输入变长；首 Token 快但总时长=输出变长或触发更多步骤 |
| 检索 | 拆 Query 改写/Embedding/向量召回/关键词召回/Rerank/文档读取，一个大 Span 无法定位 |
| 工具 | 看单次耗时、超时、错误码、重试次数、返回大小、冷启动；连续多次调用可能不是工具慢而是 Agent 没利用上次结果 |
| 编排 | 单 Span 都不慢但整条 Trace 很长：Planner 拆太细、反思反复推翻、路由绕路、无依赖工具被串行 |
| 重试 | 单次失败 1 秒，多轮退避后总时延暴涨；每次尝试单独记录并关联同一逻辑调用 |
### 对症优化
- **排队**：扩容、隔离优先级/租户工作负载、并发上限+背压+准入；请求携带端到端截止时间，下游不再执行来不及返回的任务；不能只靠加机器；
- **模型**：任务难度做模型路由（简单任务给小模型）；稳定前缀用缓存；裁剪无关上下文；约束超长输出；**切换模型或缩短上下文后必须重新验证质量**；
- **检索/工具**：独立调用安全并行、有批量接口优先合并、高频结果可缓存；连接复用、索引优化、返回字段裁剪；下游持续异常要有超时、熔断、降级；
- **编排**：无依赖子任务用 DAG 并行调度；Planner/Executor/Reviewer 有清楚完成标准与停止条件；设步数/时间/Token/重试预算，连续无进展及时换路或停止；
- **重试**：按错误类型判断是否值得重试；临时限流有界退避+随机抖动；参数/权限错误原样重试无意义；**有副作用工具必须带幂等键**，避免超时重试造成重复扣款、重复发消息；
- **验证**：历史轨迹回放 + 灰度 + 分位数对比，同时盯任务成功率、答案质量、安全和成本，不能只把耗时压下来。
## 🎯 面试总结
- 答题框架：先定义「慢」（TTFT vs 总时延、分位数、切片口径）→ Trace 结构设计（Trace ID 串联、Span 属性、敏感数据脱敏、采样策略）→ 定位四步（指标圈范围→对比快慢 Trace→瀑布图关键路径→下钻日志指标）→ 六类瓶颈特征 → 对症优化+回归验证；
- 高频追问点：为什么平均值不可信、为什么 Span 耗时不相加、流式输出为何不缩短总时延、重试与幂等的关系。
