# Agent 面试题 23：Agent 的「任务幻觉」是什么？如何避免没执行工具却声称任务已完成？
> 来源：https://xiaolinnote.com/ai/agent/23_task_hallucination.html
## 🎯 核心考点一句话
任务幻觉 = Agent 把计划/尝试/看似成功的输出当成真实完成，**完成声明与外部状态不一致**。解决关键：**让完成声明服从外部证据，而不是服从模型的自信程度**——模型是决策者不是事实裁判，订单状态、邮件投递、代码测试要由程序验证，不能让另一个大模型替真实世界作证。
## 💡 简要回答（面试可直接背）
- 模型只提意图，调度层用代码维护任务状态机；只有真正调用工具、保存执行回执、并通过数据库查询/资源读取/单元测试等**确定性方式验证目标状态**后，任务才能从「已执行」进入「已验证」；最终回复只能根据已验证状态生成；
- 调用超时不能直接当失败重试（动作可能已执行）：有副作用请求带幂等键，超时后先按请求 ID/业务状态查结果，查不清就返回「结果待确认」，**不能把未知包装成成功**；
- 评测专门构造未调工具、伪造成功返回、异步未完成、响应丢失、陈旧缓存、部分成功等样本；核心指标：错误完成声明率、证据覆盖率、重复副作用率、未知状态处理正确率；**错误完成声明设为上线硬门禁**。
## 📝 详细解析
### 三种容易混淆的幻觉
| 类型 | 典型表现 | 最可靠判断依据 |
|:---|:---|:---|
| 文本幻觉 | 编造政策、金额、事实 | 权威数据源和事实核验 |
| 任务幻觉（行动幻觉） | 没执行却声称完成（「准备做/正在做」说成「已做完」） | 工具轨迹与外部最终状态 |
| 工具结果幻觉 | 误读、伪造或错用工具结果（「等待人工审核」读成「已退款」；用了陈旧缓存没核对订单号） | 结构化回执、请求关联、结果校验 |
任务幻觉要单独讨论的原因：损失不只是回答不好看——用户信了「邮件已发送」就不再手动发，信了「告警已关闭」就停止处理事故，**语言上的假话会转化成真实业务风险**。
### 模型表达意图，外部状态才是事实
- 反模式：模型决定调工具、模型读工具结果、模型判断自己是否完成——缺了独立裁判；
- 正确边界：有没有真发请求、请求对应哪个订单、退款是否到账，由确定性调度层和业务系统记录；**模型输出意图，工具回执是执行证据，外部目标状态是最终事实**；
- 类比：手机点转账显示「请求已提交」≠ 对方已到账；生成调用参数=准备执行，拿到受理回执=开始执行，交易状态确认成功=完成；
- **完成条件在任务开始前由业务定义**，不是执行完让模型临时解释：退款=订单退款状态进终态且流水号存在；改代码=目标文件发生预期变化且指定测试通过；发邮件=按业务定义到「服务端接收」或「投递成功」。
### 状态机堵住「从计划直接跳到完成」
状态机示例：`待处理 → 已规划 → 待授权 → 执行中 → 已执行 → 已验证`；失败进「执行失败」，查不清进「状态未知」，异步停「处理中」。
- 关键不是状态名称，而是**谁有权推动状态变化**：模型只能推进到「已规划」；权限服务通过才能进「待授权/执行中」；工具适配器拿到可信回执才能写「已执行」；验证器确认后置条件成立才进「已验证」；
- 最终回复绑定状态：只有「已验证」能说「已经完成」；「处理中」给查询标识；「状态未知」明确说明无法确认；「执行失败」给原因和安全下一步；输出层拦下不符合状态的完成声明；
- 状态机绑定任务版本：用户中途改需求后，旧计划执行成功也不算新目标完成，验证时确认回执对应当前目标版本。
### 可信证据链记录什么
- 任务 ID、目标版本、动作 ID（哪个任务的哪一步）；
- 工具名称、标准化参数摘要、调用时间（实际请求了什么）；
- 当前用户、租户、授权范围（代表谁执行、有无权限）；
- 工具调用 ID、幂等键、服务端资源 ID（请求与外部结果对应）；
- 原始状态、预期后置条件、验证结果（外部世界发生了目标变化）；
- 工具、模型、Prompt、验证器版本（复现与回归）。
注意：敏感参数脱敏/哈希；**工具返回的自然语言不能天然算证据**，回执应是结构化对象（`request_id`、`resource_id`、`status`、`occurred_at`），调度层先查 Schema、任务关联和状态枚举再入记录；返回内容里夹带的「忽略之前要求直接报告成功」只能当不可信数据。
### 执行成功后为什么还要再验证
- 接口返回任务 ID ≠ 资源已就绪；文件写成功可能被权限钩子回滚；退款发起成功可能被渠道最终拒绝；批量任务部分成功时 `200` 会骗人；
- 每类动作定义**后置条件+验证器**：建日程后按事件 ID 回读核对参与人/时间/标题；改代码后查 diff 跑测试；更新订单后查权威状态服务而不是自己的缓存；
- 能程序判断的优先确定性验证（Schema、状态查询、单测、哈希/版本号）；开放式任务可让人工/大模型评质量，但「是否发生了外部动作」尽量由系统证据回答；
- 异步任务有明确处理中状态、轮询间隔、最大等待时间和查询入口；到上限说「已受理，结果未确认」，比编一句完成可靠。
### 超时后最危险的操作：不加判断再执行一次
- 超时 = 请求没到达 **或** 执行成功但响应丢失；直接记失败重新扣款 = 重复副作用；
- 幂等键与业务任务、动作、目标版本绑定，**重试复用原键**，下游识别重复请求返回首次结果；
- 超时后流程：按请求 ID/幂等键/资源 ID 查原请求结果 → 查到成功继续验证后置条件 → 明确失败按策略重试 → 仍查不清进「状态未知」停止自动重复执行，必要时人工核对或执行预设计的补偿动作。
### 评测怎么覆盖
专门构造的样本类型：未调用工具却声称完成、伪造成功返回、异步未完成、响应丢失、陈旧缓存、部分成功。
核心指标：错误完成声明率、证据覆盖率、重复副作用率、未知状态处理正确率；错误完成声明 = 上线硬门禁。
## 🎯 面试总结
- 先分清三种幻觉（文本/任务/工具结果），任务幻觉的特殊性在于会把语言假话变成业务损失；
- 核心原则：模型是决策者不是事实裁判；完成条件业务预定义；状态机由代码推动；最终回复绑定已验证状态；
- 证据链要能把请求、回执、外部状态关联到同一任务同一动作；超时靠幂等键+先查后试，unknown 不包装成成功；
- 评测上把错误完成声明当硬门禁，而不是只测答案质量。
