# Agent 面试题 12：Agent 记忆压缩通常有哪些方法？
> 来源：https://xiaolinnote.com/ai/agent/12_memcompress.html
## 🎯 核心考点一句话
记忆压缩有**四个不同维度的方法：滑动窗口、摘要压缩、重要性过滤、结构化抽取**——它们不是互斥或按优劣排列的，而是分别解决「历史太长怎么截」「内容不等价怎么挑」「对话文本是不是最佳载体」的问题，实际系统通常组合使用。
## 💡 简要回答（面试可直接背）
- **摘要压缩**：把长对话总结成简短摘要，用摘要替换原始历史；
- **滑动窗口**：只保留最近 N 轮对话，超出的从最老开始丢；
- **重要性过滤**：给每条记录打分，按价值而非时间决定去留；
- **结构化抽取**：把关键事实抽成结构化字段（如用户偏好、已确认决策），替代对话文本注入 prompt。
- 工程上最常用的是**滑动窗口 + 摘要的组合**：窗口控制长度上限，丢弃前先做一次摘要提炼，尽量不做硬截断。
- 补充加分项：**Prompt Caching 是「计算层」优化**（缓存前缀计算结果、降本降延迟），和「信息层」的记忆压缩是互补关系，不是替代。
## 📝 详细解析
### 问题根源：context window 限制 + 成本压力
- LLM 没有持续记忆，每次生成都依赖「调用时传入的完整 messages 列表」，这个列表有硬上限（GPT-4o 128K、Claude 默认 200K，部分模型付费可扩到 1M）；超限默认「从最老的对话开始丢」，于是 30 分钟前确认的关键决策就被扔掉了；
- 即使没超限，对话越长每次调用输入 token 越多，**高频场景下是真实的成本压力**；
- 记忆压缩要解决的就是两件事：**在保留关键信息的前提下，减少历史占用的 token 数量**。
### 方法一：滑动窗口——最简单也最粗糙
- 做法：超出窗口就从最老的开始删，只保留最近 N 轮；
- 优点：实现极简，零额外 LLM 调用、零额外开销；
- ⚠️ 本质缺陷：**硬截断**——按时间一刀切，三周前确认的关键决策和昨天的闲聊被同等对待，超出窗口就永久消失（「金鱼记忆」）；
- 适用：短对话、历史信息不重要的场景，成本最低。
### ~~方法二~~：摘要压缩——丢之前先提炼一遍
- 核心思路：不直接丢弃即将超出窗口的历史，先让 LLM 总结成精华摘要，用摘要替换原始对话；
- 典型用法：「**旧的压缩成摘要，近的保持完整**」——最近几轮和当前任务关系最密切保持原文，更早的历史压成摘要；
- 代价：摘要会丢细节——LLM 按自己判断的「重要性」取舍，当时被略过的细节后来可能需要，就找不回来了；
- **进阶：层级式摘要（Hierarchical Summarization）**：分层压缩，如最近 10 轮保持原文、10~50 轮压成「中期摘要」、50 轮之前压成更精炼的「长期摘要」。信息密度越久远越精炼，但核心决策始终保留；类比公司会议纪要体系（今天的逐条记录、上个月的要点摘要、去年的关键决策备忘）。Agent 既能精确回忆近期细节，也能粗略回忆远期要点。
- 🔥 **最常见工程组合：滑动窗口 + 摘要**——窗口负责控总长度上限，摘要负责丢弃前提炼，既有长度控制又不是硬截断。
### 方法三：重要性过滤——按价值筛选，不按时间筛选
- 前两种方法都在「时间维度」处理历史，但**时间 ≠ 重要性**：三周前的关键决策远比昨天的闲聊有价值，却会先被滑动窗口丢掉；
- 做法：给每条对话打重要性分数，低于阈值淘汰、高分保留。打分方式两种：
  1. **规则打分**：含「决定/确认/需求」等关键词加分、被后续引用次数多加分、纯闲聊降分——快、无额外开销，但粗糙、边界情况易误判；
  2. **LLM 打分**：逐条判断重要程度——准确率高，但每条一次 LLM 调用开销大，适合批量清理历史而非实时处理；
- 进阶思路一：**观察遮蔽（Observation Masking）**——不删除低分内容，而是在构造 prompt 时选择性「隐藏」某些历史条目。如当前任务是写代码，就跳过需求讨论的历史；进入测试阶段再把测试相关历史「显示」出来。信息没有真正删除，只是动态选择「当前最需要看到什么」，**省 token 且避免不可逆的信息丢失**；
- 进阶思路二：**主动压缩（Proactive Compression）**——不等 context 快满才被动压缩，Agent 每步执行完主动压缩中间过程。如搜索工具返回 2000 token 原始结果，读完后立刻压成 200 token 要点替换掉，**从源头控制 context 增长速度**。特别适合工具调用频繁的 Agent（工具返回的原始数据往往很长，有用的只占一小部分）。
### 方法四：结构化抽取——换一种载体存信息
- 前三种方法的共同假设是「历史以对话文本形式保留」，结构化抽取先问一个更本质的问题：**真的需要保留对话文本本身吗？**
- 真正有价值的往往是对话中的事实和状态：「用户偏好 Python」「预算上限 5 万」「已确认方案 B」——抽成结构化字段存起来，注入 prompt 时直接用字段，比传一大段对话文本高效得多、信息密度高得多；
- 类比：医生不写逐字对话记录，而是整理成结构化病历（主诉/现病史/过敏史/初步诊断），下次就诊直接读病历，不重听全程录音；
- 优点：**信息损失最小**，字段定义合理则重要信息全部被精确保留，没有摘要的模糊化；
- 代价：**开发成本最高**——需预先定义「什么是重要字段」，要求对业务深入理解，且不同任务字段可能完全不同，通用性低。
### 四种方法的关系梳理（三个维度，可组合）
| 方法 | 解决的问题 | 思路 |
|:---|:---|:---|
| 滑动窗口 | 历史太长，怎么截 | 按时间直接硬截 |
| 摘要压缩 | 历史太长，怎么截 | 截之前先提炼 |
| 重要性过滤 | 内容不等价，怎么挑 | 打破时间顺序，按价值筛选 |
| 结构化抽取 | 对话文本是不是最佳载体 | 换信息密度更高的形式存储 |
- 组合示例：先重要性过滤筛掉低价值内容 → 再摘要压缩剩余历史 → 同时对关键信息做结构化抽取。实际系统往往多种方法配合。
### 🔥 Prompt Caching：「计算层」的互补手段（加分项）
- 背景：LLM 每次处理请求都要把输入所有 token 过一遍模型（prefill），是延迟和成本主要来源；固定的 system prompt + 越来越长的对话历史，每次都被重复计算；
- 思路：**prompt 前缀在多次请求间相同，就缓存这部分计算结果，前缀匹配时直接复用**（Anthropic Claude 和 OpenAI 均已支持）；
- 费用（以 Claude 为例）：命中缓存的 token 约为正常输入的 **1/10**；写缓存有一次性额外费用（5 分钟有效期约 1.25 倍，1 小时约 2 倍），复用两次以上即回本；Agent 的 system prompt + 长期记忆注入在多轮中基本不变，天然适合缓存；
- ⚠️ 层次区分：**记忆压缩在「信息层」工作**（决定哪些内容值得保留），**Prompt Caching 在「计算层」工作**（对已决定带进去的内容减少重复计算），两者互补不替代，可同时使用。
### 工程实践决策参考
| 场景 | 推荐方案 |
|:---|:---|
| 对话不长、业务简单 | 滑动窗口（实现成本最低） |
| 对话很长但不想硬截断 | 摘要 + 滑动窗口组合（最稳健） |
| 有明确定义的「关键信息」（偏好/确认事项/状态字段） | 结构化抽取（信息密度最高、效果最好） |
| 高频调用、长 prompt、成本敏感 | Prompt Caching（收益可观，优先考虑） |
## ⚠️ 面试常见踩雷点
1. **只知道滑动窗口就停了**——面试官考的是对「压缩」的完整认识，必须覆盖四种方法并讲清各自解决的不同维度问题；
2. **认为摘要「够用了」**——摘要本身会丢细节，且当时不重要的信息后来可能需要，要意识到这个局限；
3. **混淆 Prompt Caching 和记忆压缩**——一个是计算层优化（减少重复计算），一个是信息层策略（决定保留什么），主动点出这个区别很加分。
