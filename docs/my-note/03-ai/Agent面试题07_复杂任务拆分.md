# Agent 面试题 07：复杂任务怎么做的任务拆分？为什么要拆分？效果如何提升？
> 来源：https://xiaolinnote.com/ai/agent/7_tasksplit.html
## 🎯 核心考点一句话
拆分的核心原因：**context window 有限，任务越大中间状态越多，模型很难持续追踪子目标**（「桌面太乱」）；拆分有**静态/动态**两种思路；拆完还要做**依赖分析 + 并行优化**，端到端延迟可降 40%~60%。**拆分粒度、并行优化、依赖分析**三点一起答才是完整方案。
## 💡 简要回答（面试可直接背）
- **为什么拆**：LLM 一次性处理太复杂的任务容易出错，context window 有上限，任务越大中间状态越多、越容易出错；拆成小步骤后每步聚焦一件事，准确率明显提升，且每步可独立验证和重试；
- **怎么拆**：两种思路——**静态拆分**（提前把步骤写死成固定 Workflow）和**动态拆分**（让 LLM 自己根据目标规划步骤，即 Plan-and-Execute，灵活但更难控制）；
- **拆完之后**：步骤间有依赖关系，识别出无依赖的步骤并发执行，端到端延迟可降 **40%~60%**；粒度以「原子操作」为标准，不能太细也不能太粗。
## 📝 详细解析
### 为什么要拆分？
- 失败案例：让 LLM 一次性完成「写一份竞品分析报告」，实际是搜索多竞品信息、整理功能对比、分析优缺点、写结论四件事混在一起，常见毛病：搜索阶段就掺杂分析意见、写对比表时突然引入新竞品、写到一半忘掉前面关键数据点，最终输出结构混乱；
- 🔥 系统性原因：**context window（工作台）有大小限制**。任务越大中间状态越多，桌面越乱——搜索结果、分析意见、写了一半的段落全堆在一起，LLM 很难持续追踪「我现在在做哪个子目标」。让人同时记十件事全做对，比每次只专注一件事出错率高得多；
- 拆分解决的就是「桌面太乱」：每步只做一件事，LLM 全部注意力集中，桌面干净质量自然高；
- 额外好处：**每步独立输出可单独检查验证，某步出问题只重试那一步**，不必从头跑整个任务。
### 两种拆分思路
- 注意区分概念（别混淆）：**CoT 是「一次生成里的内部拆分」**（一个回答内部把推理逐步写出，不涉及多步工具调用）；**ToT 允许同时探索多条推理路径再选优**——它们是「LLM 内部怎么把复杂问题想清楚」；而静态/动态拆分说的是「Agent 怎么把大任务切成多个独立执行的步骤」，粒度和目标不同。
#### 静态拆分
- 提前把任务流程设计好，固定成确定的 Workflow，每步做什么、按什么顺序全部事先写死。例：「写技术博客」固定拆成 搜索资料 → 整理大纲 → 逐段撰写 → 润色校对；
- 优点：行为完全可预测，出问题知道是哪一步、好排查；缺点：灵活性低，遇到没设计进流程的情况易卡住。
#### 动态拆分（Plan-and-Execute）
- 把「任务拆解」本身也交给 LLM：给目标 → 先输出执行计划 → 按计划逐步执行。即给 LLM 引入「先规划再执行」的习惯，把「想清楚要做什么」和「真正去做」分成两个独立阶段；
- 三个阶段角色清晰：
  1. **规划**（项目启动会）：只做规划不执行，输出有序步骤列表（如「AI 行业调研」→ 调研现状与市场规模 → 分析头部公司 → 梳理技术趋势 → 汇总结论 → 排版润色）；
  2. **执行**（各部门干活）：逐步执行，**每步把前面所有步骤结果作为 context 传入**，LLM 始终知道整件事做到哪里、不会「失忆」，每步只聚焦自己的任务，不会像 ReAct 那样被岔路吸引；
  3. **汇总**（项目验收会）：整合各步骤产出，还要解决衔接问题，确保最终输出连贯整体而非生硬拼接；
- 优势：灵活性强，可按任务特点制定最合适的计划；劣势：**规划质量不稳定，规划一旦出错，后续所有执行都建立在错误基础上**。
### 🔥 依赖分析与并行优化
- 拆完步骤后的关键事：分析步骤间依赖关系，识别可并行的步骤——**这是降低总耗时的关键**；
- 厨师做饭直觉：烧水、切菜、腌肉串行总时间是三者之和；并行后**总时间由「最长路径（关键路径）」决定**。并行降低的不是每步时间，而是关键路径总时间；
- 示例：步骤 3 依赖步骤 1，步骤 4 依赖步骤 2 和 3：
```python
import asyncio
async def execute_parallel_steps(independent_steps: list):
    # asyncio.gather 让多个步骤同时开始执行，不等某一个完成再启动下一个
    # 就像厨师烧水的同时切菜，两件事并发进行
    tasks = [execute_step_async(step) for step in independent_steps]
    results = await asyncio.gather(*tasks)  # 等所有并发步骤都完成，一起拿结果
    return results
# 依赖图：步骤 1 和步骤 2 相互独立，可以并行
#   步骤 3 需要步骤 1 的结果才能开始
#   步骤 4 需要步骤 2 和步骤 3 都完成才能开始
#   步骤1 ──────────────┐
#                        ├──> 步骤3 ──┐
#   步骤2 ──────────────┘             ├──> 步骤4（最终输出）
#            └──────────────────────  ┘
```
- 每步 3 秒时串行 12 秒、并行 9 秒；步骤越多、可并行越多节省越可观，**实际项目降低 40%~60% 端到端延迟很常见**（前提：依赖关系稀疏、工具 I/O 占主要耗时；若所有步骤强依赖上一步，并行空间基本为零）；
- 🔥 落地前提：**先把依赖关系画成有向无环图（DAG）**，节点是步骤、边是依赖，无依赖的节点同时跑，有依赖的等父节点完成。这步做得对不对直接决定并行优化的天花板。
### 拆分粒度：原子操作标准
- 拆太细的代价：步骤多 → LLM 调用次数多 → token 上升；每步只做极小的事 → LLM 看不到全局，产出衔接生硬；
- 拆太粗：回到原问题，每步负责太多事、出错概率上升、出问题无法定位；
- 🔥 实践标准：**以「原子操作」划分单步**——只做一件独立的事、边界清晰、做完有明确输出、和其他步骤不互相依赖；
- 例：「搜索竞品 A 的产品信息」是原子的；「整理竞品分析」不是（包含搜索、筛选、格式化三件事）；
- 判断方法：**你能给它写一个清晰的函数签名吗？** 能则大概率是原子的；若函数里还要分好几个阶段处理好几类情况，则需要再拆。
### 自适应拆分：做不好就继续拆
- 静态/动态拆分都隐含假设：拆分在任务开始时一次性完成。实际常遇到：某步比预想复杂、LLM 一次做不好需再拆细；或某步很简单拆太细浪费调用；
- 核心逻辑：**先让执行器尝试完成当前任务，做得好就继续；明显做不好（超最大步数 / 输出质量不达标）就把该任务交给规划器进一步拆成更小子任务，对每个子任务递归同样流程**；
- 例：「写竞品分析报告」一口气写完质量差 → 拆成「搜集数据 / 对比分析 / 写总结」→「搜集数据」还是做不好 → 再拆成「搜集竞品 A / B / C 的数据」，这次每步足够简单顺利完成；
- 像一棵递归展开的任务树，**只有真正做不好的节点才继续拆分**；巧妙特性：**计算开销与任务实际难度成正比**，而不是一刀切地对所有任务做同样深度的拆分。
### 执行中的 Replan 机制
- 拆完只是第一步，执行中还要问：计划需不需要调整？例：计划「查竞品 A 定价 → 查竞品 B 定价 → 对比分析」，执行第一步发现竞品 A 已停止运营，后续对比分析就没意义了；
- 做法：每步执行完，把当前结果和剩余计划交给规划模块判断「基于新信息，后面的计划还合理吗」，不合理就生成新的剩余步骤计划，**保证计划始终和实际情况同步**；
- 代价：每步多一次「评估计划」的 LLM 调用。🔥 实践折中：**不是每步都触发 Replan，而是设触发条件**——如某步输出与预期差异很大、或步骤执行失败时才启动，既应对意外又不过度消耗。
### 拆分结果的验证标准（三个条件）
1. **完备性**：所有步骤加起来能否覆盖原始任务全部要求、有无遗漏。检查法：把所有步骤描述拼在一起，与原始任务逐项对照（用户要求「市场份额、功能对比、定价策略」三个维度，步骤里必须每个维度都有人负责）；
2. **独立性**：每步职责边界是否清晰，有无两步做同一件事、输出重叠。反面例子：步骤 2「搜索竞品 A 的产品功能」与步骤 3「分析竞品 A 的核心能力」边界模糊、大概率搜到同样内容导致重复劳动；更好拆法：一个只负责搜集、一个负责加工。职责重叠不仅浪费 token，还可能导致汇总时出现矛盾评价；
3. **可验证性**：每步执行完能否用简单标准判断做对了没有——直接决定能否做自动重试和质量把控。例：步骤「搜索竞品 A 定价信息」在拆分时就定义验收标准「输出必须包含价格数字和计费模式（按量/包月/免费增值）」，执行完自动检查、缺了自动重试。**好做法：步骤定义和验收标准成对出现，像写单元测试断言一样**。
## ⚠️ 面试常见踩雷点
1. **只说「每步简单了更容易做对」**：不够准确。核心原因是 context window 有限、中间状态太多导致模型难以持续追踪子目标（「桌面太乱」）；
2. **混淆 CoT/ToT 与任务拆分**：前者是一次生成内部的推理拆分，后者是 Agent 把任务切成多个独立执行的步骤，粒度和目标不同；
3. **漏掉拆分后的工程动作**：拆完不算完——依赖分析（DAG）、并行优化（关键路径降延迟）、Replan（计划与实际情况同步）、粒度把控、拆分结果三标准验证，才是完整方案。
## ✅ 答题 checklist
- [ ] 第一层「为什么拆」：context window 有上限、任务越大中间状态越多越易出错，拆开后每步可独立验证和重试；
- [ ] 第二层「怎么拆」：静态拆分（写死步骤，适合流程固定场景）vs 动态拆分（Plan-and-Execute 三阶段：规划/执行/汇总，灵活但规划质量不稳定）；
- [ ] 第三层「拆完还要做什么」：依赖分析画 DAG、能并行的并发跑（关键路径延迟降 40%~60%）、执行中按条件触发 Replan；
- [ ] 加分项：自适应拆分（做不好就递归再拆，开销与难度成正比）；粒度以原子操作为标准（能否写出清晰函数签名）；拆分结果三标准——完备性、独立性、可验证性（步骤定义与验收标准成对出现）。
